# Phase 4 increment 3 implementation scope

**Question.** Can one operator-initiated request give the isolated adapter exactly one opportunity to send the approved projection to the approved provider endpoint?

**Baseline.** Increment 2 is on main at `bc06e4db17df75aa45459da9f92d44a2d30f3aba`, tree `b745487a36a8b14c9b6b7d8ffe5cfd56e86f0a33`. Proto owns the adapter and operator workflow. Proto approved the boundary, the four package budgets and the conditional use of libcurl. The [provider contract](../contracts/model-proposals.md#phase-4-boundary-specification) fixes the profile and limits. [ADR-0010](../decisions/0010-provider-adapter-boundary.md) and [ADR-0011](../decisions/0011-atomic-model-request-consumption.md) govern authority, issuance and consumption.

## Approved boundary

Expose one provider-independent operation to the caller. Its inputs are the live issuer's request ID, pinned catalog revision and identity, remaining BOOTTIME deadline, and cancellation signal. Its result is bounded candidate bytes or a typed failure. The deadline is local control metadata. Only the fixed instruction, schema, opaque ID and selected public or synthetic example enter the model context. Build the example from the immutable catalog. Reject an unknown revision or identity before opening a connection.

Use a short-lived adapter front end with an inherited local channel and no Internet sockets. A separate trusted, one-shot transport owns the dedicated adapter credential and constructs the fixed HTTP request. The trusted launcher binds the transport to the issuer's tuple once. The front end cannot choose the request ID, body, hostname, port, method, path or headers. It receives the bounded response for envelope extraction. Only the transport runs as the credential-bearing adapter identity. The runtime, operator CLI, front end, marker worker and fixture recorder receive no bearer token. Neither adapter process has a store handle, custody socket, approval role or worker descriptor.

Use an externally enforced network boundary for the transport. A trusted resolver/connector resolves only the configured hostname, vets the answers, chooses one eligible address, and confines that attempt to that address on TCP 443. Bind the actual connection to the vetted address and verify the peer address. Preserve the original hostname for TLS SNI, certificate verification and HTTP authority. Deny mixed allowed/denied answers, private and other disallowed address classes, including equivalent IPv4-mapped IPv6 forms. Enforce denial of additional connections, alternate endpoints, direct DNS, ambient proxies and local services outside the front end. The launcher and transport are trusted for call construction. An address filter cannot inspect an encrypted HTTP method or path.

| Design choice | Benefit | Cost or limit |
|---|---|---|
| Fixed-request transport plus external connection policy (selected) | Separately enforces what can be sent and where it can go. A hostile front end cannot turn the interface into a general HTTPS client. | Adds a trusted process, a narrow IPC format, peer authentication, and kernel qualification. |
| Generic HTTPS client with a destination firewall | Fewer processes and simpler deployment. | Other methods, paths and bodies on the allowed host remain possible. This falls short of the agreed call boundary. |
| General TLS-intercepting proxy | Can inspect HTTP centrally. | Introduces another key/trust boundary and a component that can see raw traffic and credentials. The single fixed operation does not require that surface. |

**Transport dependency decision.** Proto approved the pinned Odin curl bindings with a Linux libcurl/TLS backend subject to qualification in 3b. Record the build and version of the libcurl library actually linked on x64-review, its enabled features, the TLS backend by name, and the identity and source of the trust roots it actually uses. Demonstrate certificate acceptance and rejection against those roots. Record fixture and production trust configurations separately. Package 3c owns external destination enforcement.

## One call and its result

1. Consume the one-shot **send opportunity** before the first outbound attempt. Only the live issuing execution can hand it out, once per issuance. Closing, cancelling, crashing or losing the response ends it. Restart cannot recreate it from a durable ID. This is separate from ADR-0011 consumption, which happens only with kind-11 intake. Production wiring of the handoff belongs to operator-workflow integration. The harness must exercise duplicate delivery and issuer loss through the same one-shot interface.
2. Send one non-streaming HTTPS POST to `api.openai.com:443/v1/chat/completions`, TLS 1.2 or later, with the exact pinned model, `n=1`, tools disabled and `store=false`. Compile the URL into the transport, restrict libcurl to the HTTPS scheme and allocate a fresh handle for each issuance. Use a deterministic request builder and a fixed catalog-to-intent mapping. Cap the serialized body at 16 KiB before connecting. Use one address, one connection and at most one HTTP request. Disable redirect following, retries, connection reuse, fallback, proxy lookup (including environment overrides) and automatic content decompression. Emit the Authorization header only after successful peer authentication. [API operation](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) · [Pinned snapshot](https://developers.openai.com/api/docs/models/gpt-5.4-mini)
3. Set the total deadline to the earlier of issuance expiry and 30 seconds from call start. Cap resolution, connect and TLS setup together at five seconds and the remaining total budget. Set libcurl connect and total timeouts to the remaining stage budgets. Enforce the deadline and cancellation in transfer callbacks using fresh BOOTTIME, and check on entry to each blocking stage and on return. At equality, cancel, close, reap and return a typed failure. A response received near expiry grants no extension for intake COMMIT. Keep the SQLite writer gate free during the call.
4. Bound cumulative bytes in the upload, header and body callbacks. The upload callback also enforces the 16 KiB request ceiling. Count all received HTTP header bytes cumulatively against 16 KiB, including interim responses and trailers. Bound the body at 64 KiB while reading, including when length is absent or chunked. Reject compressed content, ambiguous framing, non-success status and incomplete transfer. Reject over-limit input before growing buffers beyond the cap. Close the connection on failure.
5. Require a single complete JSON chat completion for the selected model with one index-zero assistant choice, a normal stop and one text content string. Reject duplicate keys in interpreted objects, refusal, tool/function calls, streaming frames, truncated output, missing or conflicting fields and trailing content. Discard unrelated provider metadata. JSON-unescape the content once, require valid UTF-8, enforce the 8,192-byte candidate cap, and pass the exact bytes to increment 1's validator. Preserve a candidate rejection as a separate result from an envelope failure. Neither parser repairs the provider's output.
6. Return a typed disposition for projection denial, unavailable credential/profile, destination denial, TLS failure, timeout, cancellation, rate limit, HTTP failure, size/framing failure, refusal, invalid envelope or invalid candidate. Retain only the request ID, profile ID, bounded counts and typed reason in failure evidence. Suppress raw bodies, provider error text, keys, TLS key logs, verbose client traces and core dumps. The adapter has no audit writer. The harness verifies sanitized records; custody-backed recording through the operator workflow remains an integration obligation.

## Acceptance fixtures

The decisive control sends one request to a synthetic TLS server in an isolated network with no public route. Use the fixed production hostname, an eligible address confined to the fixture network, a test CA supplied by the fixture deployment and a synthetic credential. Keep fixture DNS, trust roots and credentials out of production configuration overrides. Independently observe the actual peer and request count, and compare method, authority, path, safe headers, model options and projected bytes at the server. Verify the synthetic credential in memory and record only whether it matched. The same validator must return the same identity, request ID and length from the extracted content and the direct fixture. Neither path starts marker intake.

| Case | Required observation |
|---|---|
| Blocked before network | Unknown catalog selection, unclassified field, expired issuance, oversized request and unauthorized local peer yield zero upstream requests. Test each byte cap at its exact limit and one byte over at the layer that enforces it. |
| Destination and TLS | Deny unexpected host/port, disallowed IP, mixed or changed DNS answers, untrusted CA, wrong hostname and old TLS. Show the forbidden endpoints are reachable by an authorized control. Count attempted connections independently and verify zero credentials at any unintended destination. |
| Same host, wrong call | Attempts to supply another method, path, model, body, header or proxy are refused at the IPC boundary. Set proxy environment variables to a reachable fixture proxy and verify zero proxy connections. Redirects to both same and different hosts produce zero follow-ups. The front end and worker cannot bypass the transport. |
| Time, cancellation and duplicates | Stall DNS, TLS, headers and body independently. Cancel before send and after the server receives it. Exercise deadline equality, 429/5xx, lost reply, duplicate handoff and process death/restart. Pre-send rejection or cancellation yields zero upstream requests. After the server has received the request, success, cancellation, timeout and lost reply each leave its count at exactly one, including after a duplicate handoff or restart. |
| Framing and parsing | Exercise header/body caps under fragmented and chunked input, compression, truncation, malformed/duplicate envelope fields, multiple choices, refusal and tool output. A valid envelope with an invalid candidate produces the original parser rejection. |
| Redaction and provenance | Put recognizable synthetic canaries in excluded context, errors, provider metadata and candidate text. Verify excluded inputs never enter the request, raw provider traffic never enters retained artifacts, and an earlier reply cannot influence the next projection. Assert unchanged store and custody and zero worker launches. |
| Actual enforcement | Inspect UIDs, inherited descriptors, credential access, effective network policy and broker lifetime. Drive allowed and denied calls on the same deployed binary. A configuration listing alone cannot qualify denial. |

## Activation handoff

The offline record can qualify the implementation and confinement on the selected kernel. A successful call to OpenAI remains **live evidence owed**. Before any live activation, Proto verifies effective voluntary input/output sharing is disabled for the dedicated API project and records project identity, date, verifier and disposition without secrets. Each request independently sets `store=false`. Preserve the accepted public/synthetic projection and the provider's documented abuse-monitoring terms. A missing or ambiguous settings verification withholds activation. [Provider sharing controls](https://help.openai.com/en/articles/10306912-sharing-feedback-evaluation-and-fine-tuning-data-and-api-inputs-and-outputs-with-openai) · [Retention terms](https://developers.openai.com/api/docs/guides/your-data)

A separate owner authorization names the reviewed source/tree, target, provider profile, project and permitted live call. Record the sanitized call count, deadline, destination, snapshot, validation result and disposition. Model unavailability is a typed failure and leaves the positive live proof open. Wiring the full operator flow, changing the project phase declaration and enabling production egress retain their existing gates.
