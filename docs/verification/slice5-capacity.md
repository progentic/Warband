# Slice 5 capacity checkpoint

Use the [Slice 4 examination rule](slice4-capacity.md) on source `457dbe9` and x64-review. Run three paired repetitions, one fresh isolated store per arm and one confirmed task per store. The control has zero denials. The other arm has one runtime-UID administrative denial generated by a separate process during the issuer's writer-lock interval, after releasing the claim barrier and before releasing the return barrier. Both arms use the same synchronization. This comparison measures work, with scheduling allowed to vary.

Preflight: each arm has at most eight events and eighteen custody frames. Fewer than 100 exchanges suffice for gate, reconciliation and acceptor, each debiting at most 37. Fewer than 100 prefix scans of at most eight rows plus three acceptance-reference reads each keep the ordinary pass well below 80,000 debits. Recheck the actual debit totals from the capture. First verify the empty-start oracle (one genesis validation and one selection visit, exchange charge 3) and the four seed custody validations (1, 2, 3, 4). Count one task only after verifying the confirmed kind-7 event and unique attempt binding.

Record startup recovery, operator index preparation, task/proposal seeding, issuer, acceptor and exact retry separately. The task numerator includes the real custody scans for the seeded input events, all issuer and acceptor examinations and any denial-generation scans during the interval. SQLite creation of the first two fixture rows has no production runtime scan. Count the evaluator's independent read of the persisted observation body and the store's accepted-claim/evaluation/observation resolution reads. Exclude scalar aggregates, derived-index rows and harness inspection using the Slice 4 rule. Sum actual positive budget increments across session resets. The fixture's seed client uses no production session budget. Report empty startup and exact retry as absolute costs since neither confirms a new task.

## Results on x64-review, 2026-11-21

All three pairs produced these counts. Each arm used one task per fresh store. Each total covers the seeded task/proposal custody requests, the gate and the acceptor. The empty recovery, index setup and exact retry have their own rows.

| Phase | No denial: actual / charged | One concurrent denial: actual / charged |
| --- | ---: | ---: |
| Empty startup recovery (fixed) | 2 / 3 | 2 / 3 |
| Explicit index provisioning (once per store) | 2 / 3 | 2 / 3 |
| Seed task and proposal | 10 / 0 | 10 / 0 |
| Gate through confirmed evaluation | 203 / 314 | 297 / 444 |
| Acceptor through confirmed transition | 115 / 156 | 163 / 219 |
| **Total per confirmed task** | **328 / 470** | **470 / 663** |
| Exact retry (zero new tasks) | 77 / 79 | 116 / 130 |

One concurrent denial added **142 actual examinations and 193 charged visits per confirmed task**. The denial itself scanned nine custody frames. Later import and repeated history checks account for the rest. Exchange debits were 376 and 550 respectively. The other debits were 94 and 113. Each accepted task advanced the versions to 2/3 and an exact retry returned its original transition ID. The custody tips were 15 and 18 respectively.

**Provisional envelope.** For this isolated implementation and allowance of at most one denial at the measured placement, the supported envelope is **one task per store**. For scale, reserving six setup debits and ten visits for the fixture's uncharged seed, a constant-cost calculation gives floor((80,000 − 6) / (663 + 10)) = 118. That projection cannot establish a larger supported store: the reader admits one task/run and prefix costs grow with history. Unbounded denials give no positive guaranteed task capacity. Neither a production limit nor the warning threshold changed.

## Reproduction

Use the Linux build and target setup in the [Slice 4 record](slice4-capacity.md#reproduction-and-raw-format). Build the normal writer/provisioning, custodian and reconciliation tools before building the measurement binaries. Run from the checkout root:

```sh
python3 tests/measurement/build_capacity.py
sudo systemd-run --quiet --scope -p MemoryMax=256M -p MemorySwapMax=0 \
  python3 tests/measurement/task_capacity.py samples.jsonl
python3 tests/measurement/task_capacity.py samples.jsonl --report
```

The [six raw samples](slice5-capacity.jsonl) have guest/host SHA-256 `f9892b1da54fc5b2fa8fdcb2fb3e50639d6fa91c6c1ca4dd29975a38a1230f1a`. Server tuples and startup use the Slice 4 format. Gate and acceptor client tuples list embedded-frame decode, receipt inspection, prefix rows, predecessors, read-backs, acceptance-reference resolutions, evaluator reinspection, exchange debits and cumulative total debits. The last two fields report budget charges. The fixture's independent verification reads are excluded from process totals. Each competing client starts a bounded request before issuer release and completes its final byte when the resumed issuer enters its next custody exchange. Raw BOOTTIME intervals and per-request counts identify the overlap. An exploratory run without that rendezvous placed the denial later and observed a smaller overhead (+95 examinations); the reported overhead applies to the declared placement.

The guest ran Ubuntu 24.04.5 x64, kernel 6.8.0-142-generic, four QEMU vCPUs, 6144 MiB configured RAM, ext4 with commit=30 on the recorded 24 GiB qcow2/APFS stack. Writeback and flush were enabled. The pinned Linux SQLite archive hash matches Slice 4. Stores and processes start fresh with the guest page cache uncontrolled. The harness uses the existing claim/return barriers in both arms. Durations establish the synchronization points. This checkpoint measures visits. The full throughput workload and WB-EXC-001 warning/operator-action proof remain separate.
